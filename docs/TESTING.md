# 测试标准

## 目标

测试用于证明当前 `0.1.0` 产品契约，而不是保护旧实现。旧测试、旧场景和历史运行结果
都不是新开发的验收标准。

每次运行测试前，先确认断言仍符合 `PRODUCT_CONTRACT.md`。如果测试和当前契约冲突，
应删除或重写测试，不能为了旧断言向运行时增加兼容补丁。

## 测试分层

### 确定性单元测试

默认测试不访问网络，使用协议级 fake 或 mock 验证：

- 输入长度、语言、凭据和不可变原始输入；
- LLM 单一分类需求清单、双语查询和无降级语义；
- 公开仓库限制、查询执行、候选合并和独立性；
- 仓库有效性、证据来源和能力声明边界；
- 全局排序输出结构与排序原则；
- 报告只投影分析结果；
- 六阶段事件、单任务、重连、取消和超时；
- Provider 错误分类和密钥脱敏；
- Web 状态、SSE、复制和手动 Markdown 下载。

测试可以使用中立的合成输入验证结构和关系，但不得把样例业务词、仓库名单或预期结果
写入运行时，也不得通过固定同义词表让测试通过。

### Provider 契约测试

GitHub 测试至少验证：

- 必须使用非空测试 Token；
- 不存在匿名降级；
- 401、403、429、网络和单查询错误具有明确语义；
- 只接受公开仓库；
- README、目录、文件、Release 和仓库关系映射正确。

LLM 测试至少验证：

- OpenAI-compatible Chat Completions 请求；
- 输入、输出 token 统计；
- 错误响应脱敏；
- Markdown JSON 提取和结构失败；
- 不进行语义重采样或字面搜索降级。

### Web 集成测试

使用 fake Provider 运行完整六阶段，验证：

- 同一时间只有一个活动任务；
- SSE 只发送真实事件；
- 页面断开后可以重新连接；
- 用户可以取消；
- 完成结果仅在内存中存在；
- 报告不会写入项目目录；
- 页面只能主动复制或下载 Markdown；
- 失败不会暴露部分报告或凭据。

### 真实 Provider 验证

只有以下情况需要真实验证：

- 解析、查询规划或双语发现语义发生变化；
- 候选发现、证据选择或证据解释发生变化；
- 全局分析、排序提示或评分契约发生变化；
- 出现确定性测试无法判断的真实关联度问题；
- 发布前验证。

普通 UI、序列化、样式、类型整理和不改变行为的重构不要求额外调用独立评审 LLM。

真实验证分为两种强度：

- 普通语义改动先运行一个最小真实案例，用于尽早发现阶段归属问题并控制调试成本；
- 解析及其后的语义阶段准备标记完成时，运行阶段用户验收：至少五条代表不同需求类型的
  完整自然语言输入，从输入阶段贯通全部已实现阶段，并使用真实 LLM 与真实 GitHub Provider。

第二种验收不能由 fake、mock、预写解析 payload、预写仓库响应或只检查请求次数的测试替代。
真实响应只在当前开发上下文中检查，不提交为长期测试产物。

### 用户期望验收

阶段用户验收判断实际输入和实际输出，而不是只判断代码路径成功：

- 解析阶段逐条检查完整需求、核心目标、功能、约束、偏好、排除项和证据目标是否忠实，
  并检查查询是否能够召回核心项目，不能仅检查 JSON 字段齐全；组合需求还必须有独立的
  项目类型与重要子能力召回方向，不能用包含否定条件的长查询反复排列全部要求；
- 功能列表必须原子化且有序：第一项是基础能力，后续每项只表达一个独立可验证能力；否定
  条件或依赖缺失要求只能进入排除项和证据目标，不能伪装成功能项；
- LLM 单独输出不枚举次级能力的 `base_function`，其余要求只输出一个带 `kind` 的需求清单；
  正向必须条件、否定/禁止条件和偏好各自只有一个类别，
  同一底层要求只出现一次。`ParseStage` 仅按类别投影视图并拒绝完全重复项，不替 LLM 猜测、
  搬运或用词表重新分类；
- 完整解析时基础功能的 `checks` 只包含一个原子 check，原子审计后允许多个 capability checks；
  每条分类需求包含一个或多个原子 check，复合功能的通用能力与限定条件在同一需求项内分开，
  分析阶段逐 check 覆盖。确定性回归至少包含一个“语言修饰 + 操作能力”的审计产物，确认通用
  操作为 capability、限定该操作所处理内容语言的关系为 `natural_language` condition。功能不会仅因用户
  声明“必须”而把能力或限定词复制到约束；每个 check 在整个结果中只归属一个需求项。缺失、
  空数组、与 checks 不等长或缺失基础/功能能力 facet 的 `check_facets`、项内重复、跨项复用或错误类型明确使
  解析失败；本地测试不能以连接词或关键词启发式代替真实语义验收；
- 解析请求携带从当前原文确定性切分的全部 `input_units`；真实和受控输出必须通过需求的
  `source_unit_ids` 与纯背景的 `context_unit_ids` 恰好覆盖每个单元，本地构造的
  `input_coverage` 必须与需求来源一致。
  缺少附件、输入格式、限定词或排除条件所在单元，或把需求单元无理由标为背景，均不能通过
  用户期望验收；
- 完整解析之后固定执行一次同 Provider 原子审计；基础/功能项必须返回非空
  `capability_checks`，其他事实使用带 facet 的 `condition_checks`，约束、偏好和排除项禁止
  capability。缺失、重复、未知 ID 或试图改变需求结构时失败，不进行第三次 LLM 重试。受控测试
  必须验证恰好两次调用，真实测试先审查审计后的 checks，再进入高 token 分析；
- 审计后的 function condition 拒绝 preference/exclusion facet，constraint 拒绝 capability、
  preference 和 exclusion，preference 与 exclusion 分别拒绝自己的 facet 以外的值；不得把类别
  错误留给分析或报告阶段修正；
- 审计必须单独返回无部署、平台、范围和次级功能限定的 `base_requirement`；本地只允许替换基础
  文本，其他需求文本、类别、来源不可变，并拒绝与现有功能项完全重复的基础文本；
- 语言、格式、规模、范围等限定 check 必须自包含地写出它与目标能力的关系；只写“支持某
  语言/格式”而没有指出被限定操作的产物不能通过真实用户期望验收；
- 带范围、语言、规模、输入方式或运行方式限定的功能在同一功能项内拆成 capability 与独立
  condition check；真实分析分别给出状态，不能复制成 constraint 重复计分，也不能用通用功能
  证据把限定条件一并判为支持；
- 用户明确指定 GitHub 支持的实现语言时，真实解析输出单独的 `github_language_qualifier`，
  `ParseStage` 将其应用到每条查询并保留多条独立召回方向；缺字段、非法格式、只把语言当
  普通全文词或由发现阶段静态猜测后补写都不能通过；格式合法但语言标签没有逐字出现在
  原始输入中的推断必须被归一为 `null`、产生解析警告，且不得进入最终查询；
- 发现阶段逐条检查候选池中是否存在多个与核心目标直接相关、可进入证据阶段的公开仓库，
  以及高价值候选是否因过窄查询、错误语言表达、搜索范围或候选上限而系统性缺失；
- 发现允许为召回保留尚未取证的候选，但零候选、只有低关联候选，或噪声挤占候选上限导致
  现实中易于找到的直接相关项目未进入候选池，都属于失败；
- 建议候选和每条成功查询的结果必须按来源轮转合并，并保持各来源内部顺序；用多批结果验证
  先执行的查询不能在达到候选上限时排除后续查询已召回的高价值候选；
- 当普通 LLM 或 GitHub 检索能够为输入指出多个真实相关项目时，产品不得以“请求成功”、
  “结构合法”或“后续阶段会过滤”为理由接受无返回或低关联返回；
- 每条失败先定位最早责任阶段。解析语义或查询规划错误只修正 `ParseStage`，查询执行、公开
  限定、合并或候选截断错误只修正 `DiscoveryStage` 或 GitHub Provider，不在下游补偿；
- 评估可使用人工相关性判断和临时的已知候选作为参照，但不得把业务词表、仓库名单或样例
  分支加入运行时实现。

## 执行顺序

1. 运行受影响的确定性测试。
2. 运行完整确定性回归。
3. 编译检查。
4. 普通语义改动如触发真实验证，先运行一个最小案例并复用已确认的上游数据。
5. 首次真实失败后立即停止后续调用，定位所属阶段并修正，不用重复采样刷结果。
6. 单案例通过后，只有在准备关闭当前语义阶段时才继续执行至少五条输入的阶段用户验收。
7. 只有结果存在无法由正常回归和人工相关性判断裁决的语义争议时，才使用独立上下文评审
   LLM。

不得通过重复采样、切换模型或追加提示把失败结果刷成成功。只有明确的短暂网络或 Provider
故障可以进行有限重试，失败仍需记录在当次调试上下文中。

## 阶段验收

### 清理基线

- Web 和 Docker 可以启动。
- 页面只显示开发状态和凭据状态。
- 搜索明确不可用，不调用旧引擎。
- CLI、MCP、Tavily、旧评审和旧评估产物不存在。
- Provider、配置和 Web 基础测试通过。

### 输入与运行管理

- 真实六阶段状态模型存在。
- 单任务、取消、600 秒超时、断线重连和内存生命周期通过测试。
- 使用仅测试可用的受控流水线完成浏览器用户闭环：输入后可以看到真实阶段变化和 loading，
  刷新后继续当前任务，用户可以取消，并能看懂完成、失败、警告和补充发现状态。
- 浏览器闭环至少使用五条接近真实使用场景的完整自然语言需求，覆盖纯中文、纯英文和中英
  混合输入，以及功能、必须条件、偏好和排除约束。不得用 `sample request`、`controlled
  example` 等测试占位文本代替用户输入；受控流水线行为必须由测试环境决定，不能根据输入
  内容建立分支。
- 浏览器验收必须检查页面实际可见内容和控件状态；仅有 API 响应、HTML 字符串或前端代码
  关键字断言不能代替用户视角验收。
- 终态任务在服务端保留期间，页面刷新后仍可恢复该任务；失败或取消不显示部分报告，页面
  可以安全开始下一次任务。

### 解析

- 原始输入不变。
- 五条真实用户风格输入分别产生完整需求、核心目标、合理解释、功能、约束、偏好、排除项、
  双语查询和证据目标；纯中文、纯英文和混合输入的可读字段遵循报告语言。
- 解析产生 2～4 组聚焦不同召回方向的查询，每组同时包含非空中文与英文表达；不得把所有
  功能和约束堆入唯一查询。每条查询独立、简洁；后续查询不累积前序全部词项，否定条件、
  排除项和缺失性要求不进入查询。LLM 建议仓库仅接受 `owner/name`，允许为空，且不获得
  免验证资格；模型能够合理识别项目时应提供建议候选，无法避免猜测时才留空。
- 建议候选的本地格式校验只保证 owner 与 name 可安全拆分；不能用比 GitHub 更严格的账户
  正则拒绝可由 Provider 复验的真实仓库，存在性、公开性和规范名称由发现阶段判断。
- 第一组查询映射第一项基础功能；后续查询各自映射另一项适合检索的原子功能，该功能可独立
  检索时不得继续携带第一项基础功能。
- 每组查询必须通过单值 `mapped_requirement_check` 声明一个基础或功能 check；第一组必须
  映射基础 check。短审计必须依据审计后的 checks 返回最终查询；最终缺少映射、映射多个 check，
  或映射约束、偏好、排除项时解析失败；真实验收还必须确认查询文本没有夹带其他需求。
- 中文和英文查询分别只能包含 1～2 个非空 term，单个 term 最多三个空格分隔词；数量、类型或
  长度不合法时解析失败，本地拼接不得补入其他需求。
- 原始输入不变；解析结果单独写入阶段上下文，不覆盖或清洗原文。
- 缺字段、错误类型、空的必需数组、无效候选格式、无效 JSON 和 Provider 失败都明确终止
  解析；固定调用完整解析与短审计两次 LLM，不进行第三次语义重试，不用字面关键词或静态词表降级。
- 确定性验证只裁决结构并消除完全重复项，不能替 LLM 补写业务含义。
- 真实发现验证如果所有合法查询均为零结果，应先判断查询规划是否过度收窄；属于解析所有者
  的问题不得在发现阶段用静态拆词或追加查询补偿。
- 阶段完成前，至少五条输入必须各自通过真实 LLM 解析，并由实际解析结果继续进行真实 GitHub
  发现；预写的期望 payload 只属于确定性结构测试，不计入真实语义验收。

### 发现

- 只搜索公开 GitHub 仓库。
- LLM 候选经过 GitHub 验证。
- 五条真实用户风格解析计划都执行去重后的中文和英文查询，不根据输入内容走静态分支。
- 搜索结果与 LLM 建议按 GitHub 返回的规范 `owner/name` 不区分大小写合并并保留原始来源；
  仓库重命名或重定向不得产生重复候选或重复复验记录。候选上限不阻止其余已规划查询执行，
  发现阶段不按 Stars 或其他指标排序。
- 私有仓库、缺少有效 `owner/name` 的响应和无法经 GitHub 复验的建议候选不能进入结果。
- 单条 422 查询失败且至少另有查询成功时产生用户可见警告；全部查询无效时失败。
- 认证、授权、限流、网络、5xx、无效响应和本地请求预算耗尽具有明确失败语义，不能与正常
  空结果混淆，也不允许匿名降级。
- 所有查询正常完成但没有任何公开候选时明确失败。
- 阶段完成前，至少五条输入必须实际贯通输入、解析和发现。每条在现实中存在相关公开项目的
  输入都应召回多个直接相关候选；零结果、仅低关联结果或相关候选被候选上限系统性挤出均
  判定为未通过，不能仅凭五份 fake 查询计划把阶段标记完成。

### 证据

- 按发现顺序最多检查 `MAX_EVIDENCE_REPOSITORIES` 个候选；每个候选重新通过 GitHub 读取规范
  元数据，不直接信任发现响应中的旧状态。
- 证据仓库包含 README、受限目录、最多三个由当前查询词动态定位的文本源码或配置摘录、最新
  Release、最后推送时间、归档、许可证、大小、fork、父仓库和镜像关系；文本材料有路径和 URL。
- 404、私有、空仓库和没有 README/目录材料的候选被拒绝，单候选失效可以继续；鉴权、授权、
  限流、网络、5xx、无效响应和请求预算耗尽明确终止阶段。
- 文件选择不依赖样例业务词、仓库名单或已知输入分支；README 与文件只做长度受限、可追溯
  的确定性摘录，不使用 Stars 排序，也不声称能力已经支持或不支持。
- fork、镜像和规范重命名仓库生成稳定同源键，供分析阶段防止重复占位；证据阶段不在没有
  内容比较时武断删除可能具有实质差异的 fork。
- 不足三个可读取证据仓库时，只允许 `DiscoveryStage` 使用原查询读取下一页补充一次，并产生
  真实补充发现事件；仍不足时失败。证据阶段不得自行生成或拆分查询。
- 阶段完成前，至少五条真实输入必须贯通输入、解析、发现和证据。人工逐条确认多个直接相关
  候选拥有足以判断核心功能与约束的 README、目录或源码材料；仅完成 GitHub 请求、只得到
  仓库简介、或只为低关联候选采集材料都不能判定通过。

### 分析与报告

- 首次分析调用在共享上下文中覆盖全部证据仓库；`candidate_decisions` 不得遗漏、重复或增加
  仓库，有效候选必须映射至少一个 capability facet 的功能需求 ID 及当前仓库正文证据，只满足
  功能限定或约束的候选无资格；请求必须把这些 ID 单独列为 `eligibility_capabilities`，输出
  只能从该列表复制，不要求模型在混合需求数组中自行过滤 facet；
  `selected_projects` 必须来自有效独立候选。第二次短调用只包含首次选出的三个项目、选择原因和
  正文证据，不包含首次逐项状态；仓库集合、候选资格和需求目录不可变，Provider 或结构首次
  失败即停止，不重试。
- 分析必须消费解析阶段提供的原子 `verification_requirements`；缺失时明确失败，不得从旧的
  平铺功能、约束、偏好和排除数组重建另一份需求目录。第二次调用只解析新的逐项状态，不能
  通过拼接并重新解析第一次候选 JSON 形成重复所有者。
- 最终三项目中，每个项目至少一个首次匹配的 capability ID 必须为支持或部分支持，否则两次
  结论冲突并失败。整体原因只汇总四种状态数量和主要确认项；风险按冲突、未确认、部分满足的
  顺序最多生成三项。fake 验证 LLM 不能输出原因、风险或分数，确定性文本与逐项状态一致。
- 分析上下文聚焦仍必须发送全部仓库；证据阶段目录只用于动态定位文件，不进入分析请求。
  README、配置和源码正文窗口只按当前查询/checks 选择、长度有界且保持原文与 URL，不得使用
  静态业务词表。长真实用例记录分析输入 token，避免发送大段无关材料。
- 每个入选项目逐一覆盖确定性需求编号，状态只能为支持、部分支持、明确不符或无法确认；
  引用只能指向该仓库实际提供的元数据、README、源码或配置证据，跨仓库引用、未知编号和
  伪造链接均使结构无效。
- 支持、部分支持和明确不符必须引用预先切分的短证据片段 ID；fake 覆盖未知编号、跨仓库编号
  和空引用。LLM 不负责复制原文，序列化、页面与 Markdown 由 ID 映射并展示对应原文；无法
  确认项可以没有引用。
- fake 必须验证目录路径不进入分析请求，且仅引用仓库元数据的支持、部分支持和明确不符会失败；
  每项用户能力判断至少还要引用一个 README、配置或源码正文片段。
- 对“不上传、不依赖、不修改、仅本地”等缺失性条件，用 fake 输出确认结构层仍只检查引用，
  并检查分析提示明确要求直接肯定证据；真实验收中任何以“README 未提及”推出 `supported`
  的结果都判定第五阶段失败，必须是 `unverified`。
- 真实验收逐项保留范围、语言、规模、输入方式和强度等限定；只证明通用全文搜索不能判定支持
  某种语言的全文搜索，只证明一般导入不能判定支持批量指定格式导入。此类仅覆盖有意义子集
  的结果必须是 `partial`，没有足够证据则是 `unverified`。
- 成功结果严格包含三个有效项目、三个互不相同的实质项目归组和唯一数组顺序；关联度是
  0～100 整数且按顺序非递增，不允许额外子评分。证据不足三个有效独立项目时明确失败，
  不发布部分结果。
- LLM fake 不输出分数；确定性测试覆盖按 parent requirement 合并 checks、状态值
  `supported=1`、`partial=0.5`、`conflicts/unverified=0`、kind 权重 `4/3/3/1`、最接近整数、
  分数非递增重排和同分保留 LLM 顺序。不得读取业务内容或修改逐项状态。
- 用合成证据验证纯链接集合、宣传仓库、普通 fork/镜像不能作为独立结果，归档、无许可证或
  长期未更新只进入事实和风险而不被确定性代码硬淘汰。
- 报告逐字段投影分析结果，不重排、不重新评分、不增加结论；证据编号映射为原 GitHub 路径
  与链接，仓库元数据保持原值。
- 运行管理器仅在流水线及资源关闭成功后保存报告；失败、取消、无效分析和关闭失败均不暴露
  部分报告。公开只显示 LLM 输入、输出和总 token，不显示 GitHub 请求或内部 trace。
- Web 用户验收检查三个结果的可见顺序、分数、原因、满足项、缺口、证据、仓库事实和风险，
  并实际验证复制 Markdown、浏览器下载、刷新恢复及下一次任务替换内存结果。
- 第五阶段关闭前使用至少五条更长的真实自然语言需求，每条包含完整场景和多种强度条件，
  从输入贯通报告并实际调用配置的 LLM 与 GitHub。逐条人工判断前三名及每项状态是否符合完整
  输入，而不是只看仓库名称或 JSON 合法；第一条异常立即停止，定位最早责任阶段后最小修复。

## 产物规则

测试缓存、真实报告、trace、截图和 Provider 响应都不得作为长期仓库资产提交。真实验证
只在当前开发上下文中检查，完成后清理。任何保存的临时内容都必须脱敏。
