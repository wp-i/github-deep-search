## 已确认且不再重复讨论的产品方向

- 产品接收一次自然语言输入，单向执行，不向用户追问，由 LLM 对合理解释作出最终断言。
- 输入最多 2000 个字符；支持中文、英文和混合输入。只要存在中文，报告使用自然中文并
  保留技术名词。
- 唯一用户入口是 Web；不提供搜索 CLI 或 MCP。Docker 保留用于本地运行。
- GitHub 是唯一发现和证据数据源，只访问公开仓库，并且必须使用 GitHub Token；不允许
  匿名降级，不使用 Tavily 或通用网页搜索。
- LLM 只承诺 OpenAI-compatible Chat Completions。解析结果结构无效时失败，不进行第二次
  语义修复，也不退化为字面关键词搜索。
- 产品执行真实的“输入 → 解析 → 发现 → 证据 → 分析 → 报告”六阶段。证据不足时允许在
  预算内进行受限补充发现，但不能无限循环。
- 成功结果固定为三个真实、公开、有效且相互独立的项目；不足三个时整次运行失败，不填充
  无关、重复或无证据仓库。
- 排序的唯一核心是项目与用户完整输入的关联度。核心功能覆盖优先于开箱即用程度；用户
  明确约束产生高权重影响但不作硬排除；最近代码推送时间是重要的次级因素。
- 免费、移动端、MCP 等只是用户可能提出的普通约束，不建立任何特定业务规则。Stars 和
  Fork 数默认不参与排序，除非用户明确要求流行度。
- 对用户只展示一个 0～100 整数关联度分数，且只用于本次运行内部排序。证据用于支撑评分，
  不产生第二套证据分或报告分。
- 报告只投影分析结论，不生成市场机会、建设建议或决策简报。服务端不保存报告；用户只可
  在浏览器中复制或主动下载 Markdown。
- 每个进程只允许一个活动任务，不排队、不并发。断开页面不会取消任务，支持重新连接、
  主动取消和默认 600 秒全局超时。结果仅在内存保留到下一次运行或进程重启。
- 公开用量只包含 LLM 输入 token、输出 token 和总 token。
- 当前处于开发测试阶段，不发布。开发阶段成本优先；只有语义核心变化才做最小真实
  Provider 验证，不例行增加独立评审 LLM。发布阶段再以结果质量优先。

完整细则以 [产品契约](PRODUCT_CONTRACT.md) 为准。以上内容不是后续实现可自行调整的默认
参数，而是已经完成确认的产品决定。

### 第二阶段：解析（已完成）

第二阶段范围只包含 LLM 需求理解及其向发现阶段交接的数据契约。解析结果必须包含
完整需求、核心目标、合理解释、功能、强约束、偏好、排除项、中英文查询组合和 GitHub
证据目标；LLM 可以提出待 GitHub 复验的 `owner/name` 候选，但不能直接形成结果。最终实现
固定调用两次 LLM：第一次完整解析，第二次短结构审计只校正基础目标、原子 checks 及其
facet，并重建逐项映射的最终查询；审计不能改写其他需求文本、类型或来源。任一结构不合格
或 Provider 失败时明确终止，不增加静态词表、字面搜索或额外语义重试。已完成：

- 在 `models.py` 建立不可变的 `ParsedRequirement` 和 `SearchQueryPair`，解析结果只写入
  `PipelineContext.parsed_requirement`，不覆盖 `RunRequest.raw_input`；
- 建立 `stages/parse.py` 作为两次解析提示、结构审计、结构验证、精确去重和资源关闭的唯一
  所有者；`LLMClient` 继续只负责传输、JSON 提取、用量和 Provider 错误；
- 严格要求十个顶层字段、非空的完整需求与核心目标、至少一个合理解释、功能、查询组合和
  证据目标；可选数组允许为空，额外字段、错误类型、空白项和无效 `owner/name` 都明确失败；
- 无效 JSON 与 Provider 失败分别产生 `invalid_parse_output` 和 `llm_parse_failed`；失败立即
  终止，不触发第三次语义重试或字面搜索；
- 使用第一阶段的五条真实用户风格输入建立确定性解析期望，并从用户角度复核功能强度、
  偏好和排除项没有在结构化过程中丢失。

五条确定性解析产物摘要如下；完整字段和中英文查询、证据目标位于
`tests/test_parse_stage.py`：

1. 本地知识库：核心目标为可本地部署的知识库；功能保留 Markdown 导入、全文搜索和
   Docker Compose；本地部署是约束，REST API 是偏好。
2. 离线转录：核心目标为 macOS/Windows 离线桌面转录；功能保留本地转录和时间戳字幕导出；
   双平台和完全离线是约束，强制云转录是排除项。
3. 自托管看板：核心目标为团队自托管看板；权限、附件和审计日志既保留为功能，也保留原文
   “必须”的约束强度；第三方云依赖是排除项。
4. JSON 校验库：核心目标为 Python 大型 JSON 流式校验；保留自定义错误信息，并把强制
   数据库依赖列为排除项。
5. React 数据表格：核心目标为可访问的大数据量 React 表格组件；保留虚拟滚动、键盘导航
   和服务端分页，React 与无障碍是约束。

按语义变更验证规则只执行了一次最小真实 LLM 解析，使用第三条自托管看板输入。真实结果
通过结构校验，并保留权限、附件、审计日志、自托管和不得依赖第三方云服务五项约束，生成
三组中英文查询、四类证据目标和三个待 GitHub 复验的候选；未重复采样，响应未保存为产物。

第三阶段首次真实 GitHub 联调时，中英文查询均合法完成但都返回零候选，唯一候选只来自
LLM 建议复验。责任判断确认 `DiscoveryStage` 已原样执行全部计划，问题属于解析阶段把过多
条件堆入单条查询导致召回不足。因此第二阶段临时重新打开，只在 `ParseStage` 查询规划所有者
中把契约收紧为 2～4 组聚焦核心能力、替代表达和部分匹配的双语查询；发现阶段不增加静态
拆词或补偿查询。修复已通过确定性与最小真实验证，第二阶段重新关闭。

第一次收紧后的组合验证生成三组双语查询并全部合法执行，得到 8 个公开候选，但其中 7 个
来自噪声较大的中文查询，英语查询仍无候选，只有 `wekan/wekan` 明显相关。进一步责任判断
发现两项独立问题：解析输出的第一组查询仍携带过多次级条件；GitHub Provider 使用默认仓库
搜索范围，没有显式包含 README。依据 GitHub 官方仓库搜索语义，Provider 统一追加
`in:name,description,readme is:public`；解析提示则要求第一组只包含项目类型和核心能力，后续
每组只增加一种替代表达或次级能力。两处分别由原行为所有者修正，不在发现阶段静态拆词。

### 第三阶段：发现（已完成）

第三阶段范围只包含认证 GitHub 候选发现。它执行解析阶段已经生成的中英文查询，
复验 LLM 建议候选，过滤私有仓库并按 `owner/name` 合并来源；不生成新查询、不读取能力
证据、不评分或排序。正常空结果、单查询 422、认证与授权失败、限流、网络或 5xx、无效
Provider 响应和本地请求预算耗尽必须保持不同语义，只有“单查询无效且至少另一查询正常
完成”可以警告后继续。已完成：

- 建立 `DiscoveryResult`，保存公开候选、成功查询、失败查询和已复验 LLM 建议候选；结果只
  写入 `PipelineContext.discovery_result`，供证据阶段继续使用；
- 建立 `stages/discovery.py`，认证后执行全部去重双语查询，逐个复验建议候选，过滤私有或
  缺少有效名称的仓库，并按大小写不敏感的 `owner/name` 合并来源；
- 候选上限不会阻止其余已规划查询执行；发现顺序只用于稳定交接，不按 Stars、更新时间或
  任何相关度指标排序；
- GitHub 仓库搜索统一限定 `in:name,description,readme is:public`，同时覆盖名称、描述和
  README 并禁止私有结果；
- Provider 现在明确区分正常空结果、404、422 无效查询、401 认证、403 授权、429 限流、
  网络、5xx、无效响应和本地请求预算耗尽，不再把关键故障静默转换为空列表；
- 五条真实用户风格解析计划均通过确定性双语查询验证；建议候选复验、来源合并、私有过滤、
  单查询警告、全查询失败、候选上限和资源关闭均有独立测试。

最终最小真实组合验证再次使用自托管看板输入。真实 LLM 生成三组查询，第一组收敛为
“自托管 看板 / self-hosted kanban”，其余两组分别补充权限审计和附件；六条 GitHub 查询
全部正常完成，三个 LLM 建议中 `wekan/wekan` 通过复验，最终得到 53 个公开候选，其中
52 个来自 GitHub 搜索。候选池包含 `nocodb/nocodb`、`plankanban/planka`、
`opf/openproject` 等可进入证据阶段的项目；发现阶段不越权删除表面命中但尚未取证的噪声
候选。真实响应未保存，未调用独立评审 LLM。
