# GitHub Deep Search 产品契约

## 1. 产品定义

GitHub Deep Search 接收一段用户想法、需求、设计或现状描述，从公开 GitHub 仓库中
寻找与完整输入最相关、最可能帮助用户实现目标的三个项目。

用户需要能够自行配置 GitHub Token 和 LLM API，但产品不假设用户是产品经理或工程
建设者，也不面向完全不了解这些基础配置的纯小白用户。

产品是单向执行：用户输入一次，系统输出一次。运行过程中不追问、不要求人工选择解释，
最终必须形成唯一排序。

## 2. 输入契约

- 输入是自然语言文本，最多 2000 个字符，典型输入预计不超过 500 个字符。
- 支持中文、英文和中英文混合。
- 输入中只要存在中文，报告使用中文；纯英文输入使用英文。
- 技术名词、库名、协议名和代码标识保持自然写法，不进行生硬翻译。
- 所有输入都被理解为“寻找与这段描述相关的公开 GitHub 项目”，不是通用问答。
- 原始输入在整个运行中保持不变，不截断、不做静态删词或业务清洗。

## 3. 成功结果

一次成功运行必须返回三个公开、有效、相互独立的 GitHub 项目。

理想结果是开箱即用地完整满足需求；无法找到时依次降级为满足部分需求、至少满足一个
重要需求点。降级不会降低证据真实性要求。

如果 GitHub 或 LLM 失败，或者无法验证三个有效项目，本次运行失败，不返回伪造、重复
或没有证据的补位项目。

## 4. 唯一排序指标

公开只存在一个指标：项目与用户完整输入的关联度，使用 0～100 整数表示。

排序原则：

1. 核心功能覆盖占主导。
2. 用户明确提出的“必须、不能、希望”等约束根据输入语义获得相应影响。
3. 所有约束使用同一判断原则，不为免费、付费、移动端、MCP 等具体内容建立特殊规则。
4. 强约束具有较高影响，但不直接淘汰项目。
5. 功能覆盖接近时，约束满足度、开箱即用程度、证据完整性和仓库活跃度进一步决定顺序。
6. 最近实际代码推送时间 `pushed_at` 是重要因素，但不能让明显无关的活跃项目反超。
7. 老项目如果功能高度匹配、证据充分且仍可使用，可以继续获得高分。
8. Stars、Fork 数默认不影响排序，除非用户明确要求流行度或社区规模。

分数只在本次运行中用于候选间比较，不跨用户输入或运行进行横向比较。分析 LLM 先选出
最符合完整需求的三个项目并给出逐项状态；分析阶段再由这些状态统一计算分数并按分数排序，
并列时保留 LLM 的全局比较顺序。

## 5. 候选资格

有效候选可以是完整应用、库、插件、模板、SDK 或参考实现，但必须包含真实实现并至少
有一个经过仓库证据确认、与输入相关的能力。

以下内容不能成为结果：

- 私有仓库；
- 空仓库；
- 纯链接集合或 awesome list；
- 只有论文、介绍或产品宣传而没有实现的仓库；
- 与另一个最终项目没有实质差异的普通 fork 或镜像。

归档、缺少许可证、长期未更新不会直接淘汰项目。它们是排序和风险判断的输入，并必须
在报告中如实展示。

## 6. 六阶段

### 输入

验证输入、凭据和报告语言，建立运行上下文。

### 解析

LLM 理解完整输入，可以内部保留多个合理解释，并生成核心目标、功能、约束、偏好、
排除项、双语搜索组合和证据目标。解析结果使用以下单一结构：

- `complete_requirement`：不遗漏明确条件的完整需求重述；
- `core_goal`：本次寻找 GitHub 项目的核心目标；
- `reasonable_interpretations`：一个或多个合理解释，不向用户追问；
- `base_function`：最广义的项目基础能力对象，完整解析时包含一个原子 check；原子审计后允许
  至少一个 capability check，并允许原文已包含的限定以自身 facet 保留；只定义项目类别，
  不枚举次级功能，也不包含部署方式、平台、运行环境、范围或其他限定；
- `classified_requirements`：除基础能力外的唯一需求清单；每项包含 `kind`、`text` 和 `checks`，
  并包含通用的 `facet` 与一个或多个 `source_unit_ids`；
  `kind` 只能是 `function`、`constraint`、`preference` 或 `exclusion`。同一底层要求只能出现
  一次；每个功能项各自表达一个独立可验证能力。功能中附带的范围、语言、规模、输入方式或
  运行方式限定在同一功能项内拆成独立 condition check，不能藏在 capability check 中被通用
  能力一并判定，也不能复制成另一个 `constraint`。独立的正向非功能条件使用
  `constraint`，非必须偏好使用 `preference`，用户明确不接受、禁止或要求不存在的
  内容使用 `exclusion`。每项包含一个或多个原子 check；复合文本中的通用能力与范围、语言、
  规模、输入方式等限定保留在同一个用户需求项内，但必须拆成多个 check；`check_facets` 与
  `checks` 等长，逐项声明 `capability` 或对应限定维度；功能项至少包含一个 capability check，
  允许并列的独立能力分别使用 capability facet，作为分析阶段逐项
  判定的唯一验收点。功能因用户表述为“必须”而仍是 `function`，不能把其通用能力或限定词
  再复制成 `constraint`；`constraint` 只表达独立的部署、平台、运行环境等非功能条件。每个
  原子 check 在整个解析结果中只能归属一个需求项；
- `context_unit_ids`：只列出确属背景、没有形成需求的原文单元 ID；每个原子需求通过
  `source_unit_ids` 引用其来源，本地据此确定性构造 `input_coverage`。所有输入单元必须恰好
  归入一个或多个需求来源或背景列表，两者重叠或存在未覆盖单元时解析失败；
- `github_language_qualifier`：用户明确要求且 GitHub 支持的实现语言限定符，格式为
  `language:<语言>`；其中语言标签必须逐字出现在当前原始输入中（大小写不敏感），没有明确
  实现语言时为 `null`；
- `search_query_pairs`：2～4 组按同一搜索目的配对的中文、英文 GitHub 查询；每组通过唯一
  `mapped_requirement_check` 映射一个基础或功能 check，第一组必须映射基础 check；中文和
  英文分别输出 1～2 个 `zh_terms`、`en_terms`，本地只负责以空格拼接。每组
  聚焦核心能力、替代表达或部分匹配方向，不把所有功能与强约束堆入同一查询；每条查询必须能够
  独立执行，后续查询不能机械继承前一条的全部词项；单个 term 不得包装多个需求或成为完整
  条件句；
- `evidence_targets`：后续必须从 README、源码、配置或仓库元数据验证的能力和约束；
- `suggested_repositories`：LLM 根据自身知识提出的 0～8 个 `owner/name` 候选；只要能够
  有合理把握地识别直接相关或重要部分匹配项目就应提供，只有无法避免猜测时才为空，且
  不能绕过 GitHub 公开性、有效性和证据验证。本地只校验它能够安全拆分为 owner 与 name，
  不用比 GitHub 更严格的账户命名规则拒绝候选；存在性、公开性和规范名称以 GitHub 复验为准。

除中英文查询本身外，可读字段使用既定报告语言。调用 LLM 前，`ParseStage` 只按通用标点、
中文连接词和英文连接词切分并编号原文单元，不解释业务词义。`ParseStage` 再按 `kind` 将单一
清单确定性投影为后续使用的功能、约束、偏好和排除项视图，并原样保留 `facet`、来源与
`checks`，再仅按来源引用和背景 ID 构造覆盖表。随后同一解析所有者执行一次固定的原子与查询
审计调用：每个基础/功能项必须在 `capability_checks` 中返回至少一个能力 check，其他限定通过
`condition_checks[{check, facet}]` 返回；约束、偏好和排除项的 `capability_checks` 必须为空。
审计后的 function condition 不得使用 `preference` 或 `exclusion` facet；constraint 只能使用
条件 facet，preference 只能使用 `preference`，exclusion 只能使用 `exclusion`。最终类别与
facet 不兼容时解析失败，不把错误类别交给下游补偿。
审计另行返回 `base_requirement`，允许且只允许把首次基础文本收敛为无部署、平台、范围或次级
功能限定的宽泛项目类别；其他需求文本、类别和来源不可变。
审计再依据这些最终 checks 重写 2～4 组查询及其映射；不得修改需求文本、类别、来源、候选建议
或添加/删除需求。
审计必须覆盖全部需求 ID 并输出最终查询，结构无效即解析失败，
不进行第三次重试。完整解析中的 facets 只校验枚举与数量，最终类别兼容性统一校验审计输出，
避免在审计纠正前提前拒绝。首次查询只校验字段、term 预算、数量和第一组基础映射；最终审计
查询再严格校验所有组只映射审计后的基础或功能 check。限定 check 必须是自包含的关系断言，
明确指出它限定的目标能力。若功能文本是被语言、格式、范围、规模或输入方式缩窄后的操作，
审计必须先移除这些修饰得到通用操作 capability，再为每个被移除的修饰生成 condition check；
不得把原复合文本原样作为唯一 capability check。不能只写系统通常支持某语言、格式、规模或
范围。没有明确约束、偏好、
排除项或候选仓库时，对应类别或数组为空，语言限定符为 `null`，不得臆造。解析固定调用两次
LLM（完整解析与短原子审计）；确定性代码可以提取 Markdown 代码块、校验完整字段、去除完全重复项，但不得使用静态
业务词表补写、翻译或重新解释内容。任何必需字段缺失、类型错误、查询组合少于 2 组或多于
4 组、基础功能为空、建议候选超过 8 个
或候选格式错误、checks 为空、`check_facets` 数量不一致、基础/功能能力 facet 缺失、项内重复或跨需求项
复用都使解析阶段失败。本地不得根据连接词或关键词自行判断语义原子性。基础功能审计后必须
至少有一个 capability facet。强约束必须进入解析结构和证据目标，但只有在有助于候选召回时才进入查询；
后续证据与分析负责判断约束，不以超长查询代替验证。否定条件、排除项和“不得依赖某物”
之类的缺失性要求不能作为 GitHub 搜索词，因为仓库材料通常不会用否定表达描述自身；它们
只保留在排除项和证据目标中。组合需求可能没有完整匹配时，查询组合必须分别召回
核心项目类型和能够满足重要子能力的部分匹配候选，而不是用完整条件的不同排列重复搜索。
第一组查询使用项目类型和第一项基础能力；后续组各自映射另一项适合检索的原子功能，并在
该功能可独立检索时移除第一项基础能力的词项。用户明确指定实现语言且 GitHub 支持对应
语言限定符时，LLM 必须输出 `github_language_qualifier`；`ParseStage` 在解析所有者内将它
确定性应用到每条中英文查询，不能只把语言名称作为普通全文词项。没有明确语言要求时该字段
必须为 `null`，不得推断限定符；发现阶段不得补写或修改。
如果 LLM 返回格式合法但语言标签没有逐字出现在原始输入中的限定符，`ParseStage` 不应用该
可选收窄，将其归一为 `null` 并产生用户可见警告；格式非法仍是无效解析结构。这样未经用户
授权的生态推断既不会缩窄召回，也不会阻断本可执行的高召回搜索。

### 发现

通过认证 GitHub API 执行中英文查询，并合并 LLM 提出的候选仓库。LLM 候选不能直接
进入结果，必须重新通过 GitHub 验证。

每个去重后的中文、英文查询各执行一次，GitHub 仓库搜索强制限定公开仓库。候选和复验成功
的建议仓库都按 GitHub 返回的规范 `owner/name` 不区分大小写合并，并保留命中查询或原始
LLM 建议来源；仓库重命名或重定向不能产生重复候选或重复复验记录。发现阶段不评分、不按 Stars
排序，也不判断能力是否真实。仓库搜索覆盖名称、描述和 README，不能因默认搜索范围漏掉
只在 README 中说明用途的项目。LLM 建议候选必须重新读取 GitHub 仓库元数据，无法访问或
返回私有仓库时不得进入候选集。候选数最多为 `MAX_CANDIDATES`，达到上限不改变后续查询
必须执行的要求。建议候选与每条正常查询的结果各自作为一个来源，按来源轮转合并；来源内
保持 GitHub 或复验顺序。不得让建议候选或先执行的单条查询独占候选上限，使后续查询已经
召回的候选无法进入证据阶段。

GitHub 返回 422 表示单条查询无效；只要至少另有一条查询正常完成，就显示非阻断警告并
继续。全部查询无效、认证失败、授权失败、限流、网络或 5xx 整体不可用、响应结构无效、
本地 GitHub 请求预算耗尽，都会使发现阶段失败。正常完成但确实没有结果不是 Provider
错误；所有查询与建议候选验证结束后仍没有公开候选时，发现阶段明确失败。

### 证据

证据阶段只从 GitHub 采集可追溯的仓库事实，不调用 LLM，也不根据 Stars 或静态业务词表
判断关联度。它按发现顺序检查最多 `MAX_EVIDENCE_REPOSITORIES` 个候选；对每个候选重新读取
GitHub 规范元数据，并采集 README、递归目录、最多三个由当前解析查询与目录动态定位的文本
源码或配置文件，以及最新 Release。证据结果必须保留来源 URL 或仓库路径，并包含最后推送
时间、归档、许可证、仓库大小、Release、fork、父仓库和镜像关系。

404、私有仓库、空仓库或没有任何可读取 README/目录材料的候选不能进入证据结果；单个候选
失效可以继续检查后续候选。鉴权、授权、限流、网络、5xx、无效响应和本地请求预算耗尽使
证据阶段失败。普通 fork、镜像或重命名仓库按规范名称及上游关系归组，但证据阶段不在没有
内容比较的情况下臆断哪个实现更好。纯链接集合、只有论文或宣传等需要理解内容的资格判断，
由分析 LLM 统一依据证据材料完成，确定性证据代码不得使用业务关键词替代语义判断。

证据阶段不输出“支持、部分支持或不支持”的语义结论；它只交付足以让分析阶段判断的材料。
第五阶段的 `AnalysisStage` 使用一次全局候选筛选和一次三项目逐项分析，是能力状态、候选有效性、
前三名选择和同分顺序的唯一语义所有者。首次调用只判断所有候选的资格、同源关系和前三名，
每个有效候选必须把至少一个 `capability` facet 的功能需求 ID 绑定到当前仓库正文证据；只满足
部署等功能限定或非功能条件不能获得资格。第二次调用只覆盖锁定的三个项目，从零生成逐项状态
和引用，不接收首次逐项状态，也不能替换项目或重做候选资格。`AnalysisStage` 再从最终状态确定性计算公开分数并
据此排序，不重新解释证据。

候选资格不是完整需求匹配度或项目类别门槛。只要仓库具有真实实现，并且正文直接确认任意一个
capability check，即使基础功能和其他需求均有缺口，也必须保留为有效部分匹配候选；这些缺口只
影响前三名选择、逐项状态和最终分数。

如果检查现有候选后不足三个可读取证据的仓库，并且尚未补充发现，证据阶段只可请求发现
阶段使用原有 LLM 查询读取下一页一次，同时发出真实补充发现事件；不得生成新查询、拆词或
重新调用解析 LLM。补充后仍不足三个时证据阶段失败。

### 分析

首次分析 LLM 在同一次调用的共享上下文中比较全部证据仓库。确定性代码先把解析阶段的功能、
约束、偏好和排除项编成稳定需求编号；每个编号同时携带原需求文本、原子 check 与 facet，
限定 check 必须在原需求上下文中判断，不能把系统其他位置的一般语言/格式支持当成目标能力
支持该限定。再把每个仓库的元数据、关系和 README、配置或源码正文编成稳定证据编号；
不得补写业务含义、预筛候选或用静态规则评分。证据阶段的目录只负责动态定位正文文件，不作为
分析输入或可引用证据。为限制 token，全部仓库仍进入比较，但每仓库的正文材料只发送按当前
查询与原子 checks 确定性选择的紧凑有界原文窗口；窗口不得生成、翻译或改写证据，未发送内容
不能被当作不存在。

分析输出使用单一结构：

- `candidate_decisions` 必须逐一覆盖全部证据仓库，包含仓库规范名称、是否具备真实实现、资格
  判断理由、当前仓库证据编号、至少一个带正文证据且 facet 为 `capability` 的功能需求 ID，
  以及代表实质同一项目的
  规范仓库名称；无功能匹配的候选必须判为无资格，fork 或镜像只有在证据显示存在实质差异时
  才能自成独立项目；
- `selected_projects` 按 LLM 的全局比较顺序包含至多三个项目；证据中存在至少三个有效独立项目时必须
  恰好返回三个，否则返回能够验证的项目后由本阶段以“有效独立项目不足三个”终止整次运行，
  不公开部分结果；
- 第二次调用的 `ranked_projects` 必须保持相同三个仓库，只包含全部需求编号的逐项判断；每个
  项目首次映射的 capability ID 中至少一个在最终判断为 `supported` 或 `partial`，否则两次
  结论冲突并失败；不由 LLM 输出分数、整体原因或风险；
- 逐项判断状态只能是 `supported`、`partial`、`conflicts` 或 `unverified`，分别表示证据确认
  满足、仅部分满足、证据明确冲突、现有证据无法确认；解释必须引用当前仓库被提供的证据
  编号，`unverified` 可以没有引用但不得把没有出现的材料描述成事实；
- `supported` 必须直接覆盖该需求的全部限定条件；证据只证明通用能力或其中一个范围、语言、
  规模、输入方式等有意义子集时只能是 `partial`，不能把未证明的限定词省略后判为完整支持；
- 分析调用前，确定性代码把仓库材料切成长度受限、带稳定编号的原文片段。除 `unverified`
  外，每项判断必须引用至少一个当前仓库片段编号；未知编号或跨仓库引用使分析结构无效。
  LLM 不复制、翻译或改写摘录，报告由编号直接还原并显示原文，使用户能够核对判断；
- 仓库元数据只说明仓库事实和身份，不能单独证明用户可观察的能力、约束或冲突。
  `supported`、`partial` 和 `conflicts` 至少引用一个 README、配置或源码正文片段；仅引用
  元数据的分析结构无效，不由报告阶段补偿或降级；
- 对“不上传、不依赖、不修改、仅本地”等关于某事物不存在或被禁止的要求，只有 README、
  配置或源码直接肯定这种行为时才能判定 `supported`；仓库材料没有提到该行为只能判定
  `unverified`，不能用“未发现”证明不存在；
- 分数是完整需求关联度的唯一公开指标，不输出子评分。确定性计算先按
  `(kind, parent_requirement)` 合并同一原需求的原子 checks，以 `supported=1`、`partial=0.5`、
  `conflicts/unverified=0` 取组内平均，再按功能 4、约束 3、排除项 3、偏好 1 加权，最终按最接近
  的整数得到 0～100 分。分析阶段按计算分数非递增排序；并列时保留 LLM 顺序。该计算不读取
  业务词、不改变状态、不设置淘汰阈值，也不产生第二套评分。

整体相关原因和风险由最终逐项状态确定性生成，不调用 LLM：原因汇总 `supported`、`partial`、
`conflicts` 和 `unverified` 的数量并列出主要已确认项；风险优先列出明确冲突，再列出无法确认和
部分满足的需求，最多三项。它们只复述当前需求文本和状态，不添加业务结论，因此不能与逐项
判断矛盾。

首次全局输出通过结构校验且已选出三个项目后，分析阶段执行一次短逐项分析：只发送这三个
项目、同一需求目录、选择原因和已有正文证据窗口，不发送首次逐项状态。该调用只能返回相同
三个仓库和完整需求覆盖，不输出整体原因、风险或分数；不能新增仓库、改变候选资格、搜索、
补取材料或修改需求。Provider
失败、结构无效或仓库集合变化时整次运行明确失败，不重试，也不发布首次选择。

分析固定调用两次 LLM，不回头改写解析、重新搜索、修改 GitHub 事实、引用未提供的证据或伪造
缺失能力。候选资格、需求状态、同源独立性、分数和最终排序均只由该阶段拥有；确定性逻辑只
验证字段、引用、覆盖范围和仓库身份，并从状态计算分数，不二次解释语义。无效结构或无法验证三个有效独立
项目都会明确失败。

### 报告

报告阶段不调用 Provider，确定性地把分析结果投影为结构化 Web 报告和 Markdown。它按分析
顺序原样呈现三个项目，不重新推断、修改分数、重排或增加市场与建设建议。逐项状态确定性
分组成“已确认满足”和“部分满足、明确不符或尚未确认”，证据编号解析为实际 GitHub 路径
和链接；最后推送、归档、许可证和 Release 直接取自证据阶段元数据。

只有报告阶段成功且运行资源安全关闭后，最终报告才写入当前任务的内存快照。失败或取消不
公开部分分析或报告。报告同时提供结构化页面数据和同内容 Markdown；复制与下载由浏览器
主动完成，服务端不落盘。公开用量只包含本次运行累计的 LLM 输入、输出和总 token。

## 7. 用户进度

Web 必须展示真实阶段和 loading 动效，不需要百分比。用户可以看到阶段开始、阶段完成、
补充发现、非阻断警告、完成、失败和取消。

每个本地实例同时只允许一个活动任务。已有任务运行时，新请求被拒绝，不排队、不并发。
用户刷新或关闭页面不会自动取消任务；重新打开页面可以连接当前任务。

默认全局运行超时为 600 秒。用户可以主动取消。

## 8. Provider 边界

- GitHub 是唯一搜索和仓库证据数据源。
- GitHub 请求必须使用配置的 Token，只搜索公开仓库，不允许匿名降级。
- 通用网页搜索和 Tavily 不属于产品。
- LLM 只承诺 OpenAI-compatible Chat Completions。
- LLM 配置为 `LLM_API_KEY`、`LLM_BASE_URL` 和 `LLM_MODEL`。
- 无效 LLM JSON 可以从 Markdown 代码块中确定性提取，但结构不合格时直接失败，不进行
  第二次语义修复，也不降级为字面关键词搜索。

## 9. 报告契约

报告只在 Web 页面中展示，每个项目包括：

- 仓库名称和 GitHub 链接；
- 本次关联度分数；
- 相关原因；
- 已确认满足的内容；
- 明确不满足或尚未确认的内容；
- 支撑判断的仓库证据；
- 最后代码更新时间、归档状态、许可证和 Release 情况；
- 必要风险。

报告不包含市场机会、建设建议、决策简报、内部 trace、费用估算或第二套评分。

服务端不自动保存或下载报告。完成结果只保存在内存中，直到下一次任务开始或服务重启。
用户可以在页面主动复制 Markdown 或下载 Markdown；文件由浏览器临时生成。

公开只显示 LLM 输入 token、输出 token 和总 token。

## 10. 失败语义

以下情况使整次运行失败：

- 输入或必需配置无效；
- GitHub 或 LLM 鉴权失败；
- Provider 限流或整体不可用；
- LLM 解析或分析结构无效；
- 无法验证三个有效、独立项目；
- 运行超时、主动取消或报告生成失败。

单条 GitHub 查询语法无效但其他查询正常完成时，可以继续运行，不过必须向用户显示
非阻断警告。失败运行不提供不完整报告。

## 11. 当前交付阶段

当前只进行开发与测试，不发布。开发阶段优先控制成本，普通改动依赖正常回归；涉及
解析、发现、证据或排序语义时才进行最小真实 Provider 验证。发布阶段再将结果质量置于
成本之前，因为用户不应依赖反复运行才能获得有意义结果。

普通改动的最小真实验证不能代替阶段完成验收。解析及其后的每个语义阶段在标记完成、
进入下一阶段开发之前，必须使用至少五条代表不同需求类型的真实自然语言输入，从输入阶段
开始贯通当时已经实现的全部阶段，并实际调用配置的 LLM 和 GitHub Provider。fake、mock、
预写 LLM 输出和预写 GitHub 响应只能证明结构、编排与失败语义，不能证明产出符合用户预期。

阶段完成验收直接检查当次真实产物。解析必须完整、准确地保留需求强度，并规划能够召回
相关项目的查询；发现必须在现实中存在相关公开项目时召回多个可供后续取证的直接相关候选。
如果常见需求通过正常 LLM 或 GitHub 检索能够识别出多个相关项目，而产品真实流程返回零
候选，或只返回与核心目标低关联的候选，则当前最早责任阶段验收失败。失败必须先归属并修正
在解析、发现或其他当时已经实现的行为所有者内，不得把召回问题推迟给证据、分析或报告阶段
掩盖。验收用的样例、人工判断和已知项目只能存在于测试与开发评估中，不能成为运行时词表、
仓库名单或输入特判。
