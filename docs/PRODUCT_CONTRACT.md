# GitHub Deep Search 产品契约

## 1. 产品定义

GitHub Deep Search 接收一段用户想法、需求、设计或现状描述，从公开 GitHub 仓库中
寻找与完整输入最相关、最可能帮助用户实现目标的三个项目。

用户需要能够自行配置 GitHub Token 和 LLM API，但产品不假设用户是产品经理或工程
建设者，也不面向完全不了解这些基础配置的纯小白用户。

产品是单向执行：用户输入一次，系统输出一次。运行过程中不追问、不要求人工选择解释，
最终必须形成唯一排序。

## 2. 输入契约

- 输入是自然语言文本，最多 2000 个字符，典型输入预计不超过 500 个字符。
- 支持中文、英文和中英文混合。
- 输入中只要存在中文，报告使用中文；纯英文输入使用英文。
- 技术名词、库名、协议名和代码标识保持自然写法，不进行生硬翻译。
- 所有输入都被理解为“寻找与这段描述相关的公开 GitHub 项目”，不是通用问答。
- 原始输入在整个运行中保持不变，不截断、不做静态删词或业务清洗。

## 3. 成功结果

一次成功运行必须返回三个公开、有效、相互独立的 GitHub 项目。

理想结果是开箱即用地完整满足需求；无法找到时依次降级为满足部分需求、至少满足一个
重要需求点。降级不会降低证据真实性要求。

如果 GitHub 或 LLM 失败，或者无法验证三个有效项目，本次运行失败，不返回伪造、重复
或没有证据的补位项目。

## 4. 唯一排序指标

公开只存在一个指标：项目与用户完整输入的关联度，使用 0～100 整数表示。

排序原则：

1. 核心功能覆盖占主导。
2. 用户明确提出的“必须、不能、希望”等约束根据输入语义获得相应影响。
3. 所有约束使用同一判断原则，不为免费、付费、移动端、MCP 等具体内容建立特殊规则。
4. 强约束具有较高影响，但不直接淘汰项目。
5. 功能覆盖接近时，约束满足度、开箱即用程度、证据完整性和仓库活跃度进一步决定顺序。
6. 最近实际代码推送时间 `pushed_at` 是重要因素，但不能让明显无关的活跃项目反超。
7. 老项目如果功能高度匹配、证据充分且仍可使用，可以继续获得高分。
8. Stars、Fork 数默认不影响排序，除非用户明确要求流行度或社区规模。

分数只在本次运行中用于候选间比较，不跨用户输入或运行进行横向比较。并列分数不需要
额外规则，分析 LLM 仍然选出最终三个项目。

## 5. 候选资格

有效候选可以是完整应用、库、插件、模板、SDK 或参考实现，但必须包含真实实现并至少
有一个经过仓库证据确认、与输入相关的能力。

以下内容不能成为结果：

- 私有仓库；
- 空仓库；
- 纯链接集合或 awesome list；
- 只有论文、介绍或产品宣传而没有实现的仓库；
- 与另一个最终项目没有实质差异的普通 fork 或镜像。

归档、缺少许可证、长期未更新不会直接淘汰项目。它们是排序和风险判断的输入，并必须
在报告中如实展示。

## 6. 六阶段

### 输入

验证输入、凭据和报告语言，建立运行上下文。

### 解析

LLM 理解完整输入，可以内部保留多个合理解释，并生成核心目标、功能、约束、偏好、
排除项、双语搜索组合和证据目标。

### 发现

通过认证 GitHub API 执行中英文查询，并合并 LLM 提出的候选仓库。LLM 候选不能直接
进入结果，必须重新通过 GitHub 验证。

### 证据

读取仓库元数据、README、目录、关键源码和配置，确认项目实际能力与状态。证据不足时
允许在预算内回到发现阶段补充搜索。

### 分析

分析 LLM 在共享上下文中比较有效候选，产出唯一排序、三个项目、分数和判断依据。

### 报告

确定性呈现分析结果，不重新推断、修改分数或增加市场与建设建议。

## 7. 用户进度

Web 必须展示真实阶段和 loading 动效，不需要百分比。用户可以看到阶段开始、阶段完成、
补充发现、非阻断警告、完成、失败和取消。

每个本地实例同时只允许一个活动任务。已有任务运行时，新请求被拒绝，不排队、不并发。
用户刷新或关闭页面不会自动取消任务；重新打开页面可以连接当前任务。

默认全局运行超时为 600 秒。用户可以主动取消。

## 8. Provider 边界

- GitHub 是唯一搜索和仓库证据数据源。
- GitHub 请求必须使用配置的 Token，只搜索公开仓库，不允许匿名降级。
- 通用网页搜索和 Tavily 不属于产品。
- LLM 只承诺 OpenAI-compatible Chat Completions。
- LLM 配置为 `LLM_API_KEY`、`LLM_BASE_URL` 和 `LLM_MODEL`。
- 无效 LLM JSON 可以从 Markdown 代码块中确定性提取，但结构不合格时直接失败，不进行
  第二次语义修复，也不降级为字面关键词搜索。

## 9. 报告契约

报告只在 Web 页面中展示，每个项目包括：

- 仓库名称和 GitHub 链接；
- 本次关联度分数；
- 相关原因；
- 已确认满足的内容；
- 明确不满足或尚未确认的内容；
- 支撑判断的仓库证据；
- 最后代码更新时间、归档状态、许可证和 Release 情况；
- 必要风险。

报告不包含市场机会、建设建议、决策简报、内部 trace、费用估算或第二套评分。

服务端不自动保存或下载报告。完成结果只保存在内存中，直到下一次任务开始或服务重启。
用户可以在页面主动复制 Markdown 或下载 Markdown；文件由浏览器临时生成。

公开只显示 LLM 输入 token、输出 token 和总 token。

## 10. 失败语义

以下情况使整次运行失败：

- 输入或必需配置无效；
- GitHub 或 LLM 鉴权失败；
- Provider 限流或整体不可用；
- LLM 解析或分析结构无效；
- 无法验证三个有效、独立项目；
- 运行超时、主动取消或报告生成失败。

单条 GitHub 查询语法无效但其他查询正常完成时，可以继续运行，不过必须向用户显示
非阻断警告。失败运行不提供不完整报告。

## 11. 当前交付阶段

当前只进行开发与测试，不发布。开发阶段优先控制成本，普通改动依赖正常回归；涉及
解析、发现、证据或排序语义时才进行最小真实 Provider 验证。发布阶段再将结果质量置于
成本之前，因为用户不应依赖反复运行才能获得有意义结果。
