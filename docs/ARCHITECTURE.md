# GitHub Deep Search 架构

本文定义 `0.1.0` 的目标架构和依赖边界。当前运行时代码必须向本文收敛；旧引擎、
旧入口或旧测试不构成兼容要求。

## 总体数据流

```text
Web
  ↓
RunManager
  ↓
Pipeline
  ├─ InputStage
  ├─ ParseStage ───────────→ LLM Provider
  ├─ DiscoveryStage ───────→ GitHub Provider
  ├─ EvidenceStage ────────→ GitHub Provider
  ├─ AnalysisStage ────────→ LLM Provider
  └─ ReportStage
```

依赖只能从入口指向运行管理、流水线、阶段和 Provider。Provider 不得依赖 Web、报告、
测试或产品语义。报告阶段不得调用 Provider，也不得更改分析阶段的排序。

## 模块所有权

| 模块 | 唯一职责 | 不得负责 |
| --- | --- | --- |
| `models.py` | 阶段间的数据契约 | 搜索、评分或渲染判断 |
| `config.py` | Provider、预算、超时配置 | 产品模式或报告策略 |
| `run_manager.py` | 单活动任务、内存状态、订阅、取消 | 需求理解和候选排序 |
| `pipeline.py` | 六阶段编排、资源关闭、取消传播 | 阶段内部业务逻辑 |
| `stages/input.py` | 输入、凭据和报告语言验证 | 需求语义解释 |
| `stages/parse.py` | LLM 需求理解和双语查询规划 | GitHub 请求和最终评分 |
| `stages/discovery.py` | GitHub 搜索、候选合并和公开性 | 能力声明和最终排序 |
| `stages/evidence.py` | 仓库有效性和证据采集 | 根据流行度决定相关性 |
| `stages/analysis.py` | 全局比较、唯一排序和前三名 | 报告排版和 Provider 传输 |
| `stages/report.py` | 确定性 Markdown 投影 | 新推断、重新评分或重排 |
| `providers/github.py` | 认证 GitHub API 调用 | 匿名降级和产品判断 |
| `providers/llm.py` | OpenAI-compatible Chat Completions | 字面搜索降级和报告保存 |
| `web.py` | HTTP、SSE 和静态页面 | 搜索、证据和评分逻辑 |
| `serializers.py` | 内部对象到 Web JSON 的映射 | 修正上游结论 |

一个行为只能有一个所有者。新实现替代旧实现时，必须同时删除旧路径和相关测试。
默认 Web 始终注入真实六阶段流水线；测试可以替换流水线工厂，但运行时不保留“开发基线禁用”
兼容分支。`GitHubClient` 只提供当前发现与证据阶段实际使用的仓库搜索、仓库/README/目录/文件
和 Release 读取，不保留旧引擎的代码、Topic 或 Issue 搜索入口与计数器。

## 六阶段契约

### 输入

验证不超过 2000 字符的原始输入、GitHub Token 和 LLM 配置。原始输入不可改写或
截断。只要输入中存在中文，报告语言就是中文，否则为英文。

### 解析

LLM 从完整输入生成核心目标、功能、约束、偏好、合理解释、双语查询组合和证据目标。
确定性代码只验证结构、字段和去重，不通过静态词表解释产品含义。无效 LLM 结构使
解析阶段失败，不降级为字面关键词搜索。

解析 LLM 单独输出只定义项目类别的 `base_function`，每项需求同时提供原子 `checks`；其余需求只输出一份带 `kind` 的
`classified_requirements` 清单；同一底层要求只允许一个类别。`ParseStage` 把基础功能置于
功能视图首位，再按类别确定性投影为 `ParsedRequirement` 的 `functional_requirements`、
`constraints`、`preferences` 和 `exclusions` 视图，不进行第二次语义分类。其余字段包括
`complete_requirement`、`core_goal`、`reasonable_interpretations`、
`github_language_qualifier`、`search_query_pairs`、`evidence_targets` 和
`suggested_repositories`。解析调用前，本地仅以通用标点与连接词生成稳定 `input_units`；LLM
以 `source_unit_ids` 把每个原子需求绑定到原文，并只返回没有形成需求的 `context_unit_ids`。
本地据此构造 `input_coverage` 并校验覆盖闭合性，不从单元文本推断类别或补写需求。
完整解析通过后，`ParseStage` 使用同一 Provider 做一次短原子审计；请求只携带稳定需求 ID、
原需求、来源单元和首次查询。基础/功能能力通过非空 `capability_checks` 返回，其他原子事实通过带 facet 的
`condition_checks` 返回；被语言、格式、范围、规模或输入方式缩窄的操作必须先移除修饰形成
通用 capability，再把修饰写成关联到该操作的 condition，不能把复合文本作为唯一 capability。
这样既避免 checks 与并行 facet 数组错位，也让分析阶段分别判断能力与限定；本地按 ID 展平并重新构造覆盖、
证据目标和查询；最终查询只能映射审计后的基础或功能
check。缺 ID、多 ID、类别不兼容、非法查询映射或 Provider 失败都终止解析，不自动重试。
审计输出还要保持类别与 facet 兼容：function 的 condition 不能变成 preference/exclusion，
constraint 使用条件 facet，preference 与 exclusion 分别只能使用自己的 facet。
审计可通过单独的 `base_requirement` 把基础文本收敛为宽泛项目类别；其余需求文本仍锁定。
分析阶段不对复合需求整句一次定性，而是逐一使用解析保留的原子 checks 建立稳定需求编号；
确定性代码不生成或拆解这些验收点。`check_facets` 与 checks 等长，保留 LLM 给出的原子维度。
完整解析中的基础功能只有一个 capability check；原子审计后基础项至少保留一个 capability
check，原文已包含的限定可用自身 facet 保留；
功能项至少包含一个 capability check，其余项可以有
多个 check。解析结构校验拒绝空数组、
facet 数量不一致、基础/功能能力 facet 缺失、项内重复，以及
同一原子 check 被多个需求项或类别重复占有，防止分析阶段重复计分。
`search_query_pairs` 包含 2～4 组搜索目的以及非空中文、英文查询。每组通过唯一
`mapped_requirement_check` 绑定一个基础或功能 check，第一组必须绑定基础 check；绑定
约束、偏好或排除项的输出无效。每种语言只输出 1～2 个 query terms，本地以空格拼接，不翻译
或补词。每组只负责核心能力、替代表达或部分匹配中的一个召回方向；
强约束仍完整保留在约束和证据目标中，不能通过把
全部条件拼进单条查询来代替后续验证。第一组必须只使用项目类型和核心能力进行高召回搜索，
不得附带次级功能或约束；后续组必须是可独立执行的替代表达或单一子能力搜索，不能累积
前面查询的全部词项。否定条件、排除项和缺失性要求只进入解析与证据目标，不进入 GitHub
查询。`functional_requirements` 按“最广义基础能力在前、独立次级能力在后”原子化，否定条件
和依赖缺失要求不作为功能。完整组合难以直接召回时，第一组查询映射基础能力，后续组分别
映射不同的原子次级能力，覆盖项目类型及重要子能力的部分匹配方向。用户明确指定且 GitHub
支持的实现语言由解析 LLM 作为单独的 `github_language_qualifier` 输出；`ParseStage` 验证后
将其应用到所有查询。确定性代码不从普通文本猜测语言，也不在发现阶段补写限定符；模型漏掉
字段或返回非法限定符属于无效解析结构。格式合法但语言标签没有逐字出现在当前原始输入中
时，解析阶段将可选限定符归一为 `null` 并发送警告，避免未经授权的推断缩窄召回。这项原文
校验只验证 LLM 声称的语义确实来自用户输入，不维护语言或框架映射表。
建议仓库只能使用 `owner/name`，最多 8 个；模型有合理把握识别直接相关或重要部分匹配项目
时应提供，无法避免猜测时允许为空。解析只验证可安全拆分的形态，不复制一套比 GitHub 更
严格的账户命名规则；存在性、公开性和规范名称由发现阶段通过 GitHub 验证。原始输入仍只
存在于 `RunRequest`，解析结果不能覆盖它。

`ParseStage` 拥有完整解析与短审计两次 LLM 调用、结构验证和精确重复项消除。`LLMClient` 只负责
OpenAI-compatible 传输、JSON 提取、用量和 Provider 错误，不理解需求字段；发现阶段不得
修复或补写解析结果。

### 发现

执行认证 GitHub 查询并合并 LLM 提出的候选。所有候选都必须重新通过 GitHub 验证，
且只能是公开仓库。单条无效查询产生用户可见警告；鉴权、限流或 GitHub 整体失败使
运行失败。

`DiscoveryResult` 是发现阶段的唯一输出，包含去重后的候选、正常完成的查询、失败查询和
成功复验的 LLM 建议候选。`DiscoveryStage` 负责执行解析阶段给出的中文、英文查询、复验
建议候选、过滤私有仓库、按 GitHub 返回的规范 `owner/name` 不区分大小写合并候选、复验
记录与来源并应用候选数量上限；仓库重命名或重定向不能产生重复记录。它
不得生成新查询、判断仓库能力或声称支持状态。复验建议与每条成功查询形成独立候选批次。
`DiscoveryStage` 以 `min(MAX_CANDIDATES, MAX_EVIDENCE_REPOSITORIES)` 作为下游证据窗口，为
2～4 组查询方向各保留一个查询候选位置，并用窗口其余前缀容纳已复验建议；查询预留位置按
计划顺序从非空查询批次轮转取得。剩余建议与查询结果继续按来源轮转合并，所有来源内部顺序
保持不变。该有界检索优先级只防止 LLM 已给出的直接线索在证据截断前被查询批次数量挤出，
不是能力评分或最终语义排序。

`GitHubClient` 必须让调用方区分正常空结果、404、单查询 422、认证或授权失败、限流、网络
或 5xx、响应结构错误和本地请求预算耗尽。Provider 不决定某个失败是否可继续；发现阶段
只有在至少一个查询正常完成时才能把单查询 422 转成用户可见警告，其他 Provider 错误均
终止阶段。仓库搜索统一追加 `in:name,description,readme is:public`，搜索名称、描述和 README
并强制公开可见性；这些属于 GitHub 传输限定符，不改变 LLM 给出的产品语义查询。

### 证据

`EvidenceResult` 是证据阶段的唯一输出，包含可读取材料的 `EvidenceRepository`、被拒绝候选、
实际检查数量和补充发现次数。每个证据仓库包含重新读取的规范元数据、README 摘要、受限
目录、最多三个动态选择的源码或配置摘录、最新 Release，以及 original、fork 或 mirror 的
关系类型和同源键。每份文本材料保存仓库路径和可追溯 URL。

`EvidenceStage` 只调用 GitHub Provider，不调用 LLM。它按发现顺序检查最多
`MAX_EVIDENCE_REPOSITORIES` 个候选，重新验证公开性与存在性，拒绝 404、私有、空仓库和没有
可读取 README/目录材料的候选。文件选择只使用当前解析产生的英文查询词与实际目录动态匹配，
再以通用文本源码/配置路径补足；不得加入业务词表、已知仓库文件或样例分支。README 和文件
只做受限、与查询词相关的确定性摘录，不生成能力判断。

同源键使用规范 `owner/name`、fork 的父仓库或镜像 URL，使分析阶段能够避免普通 fork、镜像
重复占位；证据阶段不根据 Stars、更新时间或未经内容判断的 fork 身份排序或淘汰实现。每项
需求的支持、部分支持、明确不符或无法确认状态，以及纯链接集合、论文或宣传仓库等语义资格，
统一由 `AnalysisStage` 在共享证据上下文中判断。

现有候选不足三个可读取证据仓库时，`EvidenceStage` 可以通过注入的补充发现接口请求
`DiscoveryStage` 使用原有查询读取下一页一次，并发送 `supplemental_discovery` 事件；证据阶段
不得自行搜索或生成查询。补充后仍不足三个时失败，不得无限循环。

### 分析

分析 LLM 在共享上下文中解释证据、判断候选资格和每项需求状态，并比较有效候选；它只决定
三个独立项目、逐项状态及同分时保留的比较顺序。`AnalysisStage` 是该语义的唯一所有者，并从
逐项状态统一计算 0～100 整数关联度、排序、整体原因和风险。核心功能覆盖占主导，
用户明确约束具有较高影响；功能接近时再重点考虑开箱即用程度、证据完整性和最近代码
更新时间。首次分析调用包含全部证据仓库，只输出资格、功能需求证据映射和前三名选择；第二次
调用只包含首次选出的三个项目，不接收首次逐项状态，且不能改变项目集合或候选资格。候选
资格只能映射 capability facet；最终至少一个映射项必须得到支持或部分支持，否则明确失败。
`AnalysisStage` 只发送按
当前查询与原子 checks 从每仓库材料中确定性选择的有界原文窗口；证据阶段目录只用于动态定位
正文文件，不进入分析请求或证据编号。选择不使用静态业务
词表，片段仍保留原 URL 与稳定证据 ID。

该阶段结果是唯一排序事实。其他模块不得追加分数、阈值、tier 或重排逻辑。

### 报告

将分析结果确定性转换成网页数据和 Markdown。报告不调用 LLM，不生成市场机会、建设
建议或其他分析阶段没有产出的结论。

## 运行管理

每个进程只允许一个活动任务。Web API 的目标语义为：

- `POST /api/runs`：创建任务；已有任务时返回 `409`。
- `GET /api/runs/{id}/events`：SSE 真实进度事件。
- `GET /api/runs/{id}`：当前状态或最终报告。
- `GET /api/runs/active`：页面刷新后连接当前任务。
- `DELETE /api/runs/{id}`：取消任务。
- `GET /api/status`：凭据状态和是否存在活动任务。

阶段状态只有未开始、进行中、已完成、失败和已取消。前端不生成虚假百分比。补充发现
通过真实事件和迭代编号呈现。

运行事件使用任务内单调递增序号保存在内存中。SSE 连接可以通过 `Last-Event-ID` 或
`after` 序号重放断开后尚未收到的事件；SSE 连接关闭只结束订阅，不触发任务取消。
运行终态是完成、失败或已取消，失败和取消会将当时进行中的阶段同步置为对应终态，尚未
开始的阶段保持未开始。

浏览器断开不会取消任务。运行继续到完成、主动取消或全局超时；默认超时为 600 秒并
可通过环境变量调整。完成结果只保留在内存中，直到新任务开始或服务重启。

## 候选与证据边界

有效候选必须是公开、可访问且包含真实实现的仓库，可以是应用、库、插件、模板、SDK
或参考实现。空仓库、纯链接集合、awesome list、只有论文或宣传而无实现的仓库无效。

普通 fork、镜像和没有实质差异的同源仓库不能重复占据三个结果。归档、缺少许可证或
长期未更新不会直接淘汰项目，但必须进入分析上下文并在报告中展示。

README、源码和配置正文都是可引用能力证据；仓库简介、目录路径、Stars 和 LLM 记忆不能独立证明
能力。证据数量不是独立评分指标，证据只用于支撑与完整输入相关的判断。

## 排序边界

- 成功运行必须返回三个有效、独立项目。
- 无法验证三个项目时运行失败，不以无关或重复仓库凑数。
- 用户强约束不作硬过滤，也不为免费、移动端、MCP 等特定内容设置特殊逻辑。
- 功能覆盖差距明显时，覆盖更多的项目可以排在违反某项约束的项目之前。
- 功能接近时，满足明确约束且近期有实际代码更新的项目优先。
- Stars 和 Fork 数默认不影响排序，除非用户输入明确提出流行度要求。
- 关联度只在单次运行内比较，不承诺跨运行校准。

`AnalysisStage` 把当前解析结果编成稳定需求编号，把每个证据仓库的元数据和正文材料编成
只在本次调用中有效的证据编号。需求编号同时包含 parent requirement、atomic check 和 facet；
功能项中的限定 check 在报告中以 parent 与 check 的确定性组合显示，不翻译或补写语义。然后
通过一次 LLM 调用完成全局筛选。LLM 必须为每个证据仓库返回资格与同源判断，有效资格至少
从确定性提供的 `eligibility_capabilities` 列表映射一个带正文证据的功能需求，再返回三个项目，
不输出逐项状态或分数。结构校验通过后，
第二次短调用从零生成这三个项目的完整状态和引用；仓库集合与候选资格不可变，
失败不重试。第二次输出直接与第一次已经验证的候选决定组合成阶段结果，不把第一次 JSON
重新拼装后重复解析。确定性代码验证精确
字段集合、仓库名称、需求覆盖、证据引用归属和三个独立结果；随后按 parent requirement 合并
原子 checks，以状态值 `1/0.5/0/0` 取组内平均，并按功能/约束/排除/偏好权重 `4/3/3/1`
计算唯一整数分数、按分数排序，同分保留 LLM 顺序。计算不改状态，也不使用第二套业务语义。
整体原因和最多三项风险同样从最终状态和原需求文本确定性生成，不接受 LLM 自由补写。

需求目录保持解析分类且不重复。对于要求某项依赖、上传、修改或其他行为不存在的条件，分析
必须区分“证据直接确认不存在”和“证据没有提及”；后者固定属于语义上的无法确认，不能由
确定性代码或 LLM 以缺失材料反推为满足。

同源判断以 `canonical_project` 表示：值必须是本次证据仓库之一；实质相同的 fork、镜像或
副本指向同一规范项目，确有实质差异的实现可以指向自身。最终三个项目的
`canonical_project` 必须互不相同。证据不足三个有效独立项目时，分析阶段失败且不发布部分
排名。

## 报告与持久化

报告是分析结果的投影，只存在于 Web 页面。服务端不自动保存报告、Markdown、JSON、
trace 或评估工件。用户主动复制或下载 Markdown 时，由浏览器使用当前页面内容生成。

`ReportStage` 只把分析结果、证据事实和引用映射为 `FinalReport`，不得调用 Provider。运行
管理器仅在六阶段执行和资源关闭都成功后原子保存该报告；失败或取消快照不包含报告。Web
序列化器提供结构化项目、Markdown 和公开 token 用量，前端只负责安全文本渲染、复制与临时
下载，不在 JavaScript 中重新评分或拼接新结论。

公开用量只包含 LLM 输入 token、输出 token 和总 token。内部阶段状态用于当前任务的
进度和错误定位，不作为可下载诊断报告。

## 失败与安全

缺少凭据、鉴权失败、限流、Provider 整体不可用、无效 LLM 结构、无法验证三个项目、
超时或报告生成失败都会产生明确的阶段错误。部分 GitHub 查询失败但其余搜索能够完成
时可以继续，不过必须向用户显示警告。

错误、日志、SSE、JSON 和 Markdown 都不得包含 Token、API Key 或 Authorization
Header。运行时只访问公开仓库，不因用户 Token 拥有额外权限而读取私有仓库。
